# M6.5.3 Release Artifacts Design

## Goal

Advance `M6.5.3` by adding the missing repository-root release-artifact build path, reusing the existing frontend production build, and making Docker-build verification explicit about the current environment blocker.

## Scope

- add a root-level Docker build definition that supports `docker build -t portex:v1.0.0 .`
- replace the placeholder `scripts/build_docker.py` with a real command wrapper
- preserve the existing runner-image build path through explicit file/context arguments
- keep `web/dist/` as the frontend release artifact generated by `npm run build`
- add static tests for the new Docker build entrypoints because no container runtime is available locally
- update operator docs and handoff notes for the new artifact boundary

## Out of Scope

- do not sync package/runtime version strings from `0.1.0` to `1.0.0`
- do not add GitHub Releases, image publishing, registry push, or release automation
- do not convert the current Compose draft into a verified deployment flow
- do not bundle backend, frontend preview server, and runner into one all-in-one process image
- do not claim full `M6.5.3` completion unless a real root-level Docker build is freshly verified

## Design Constraints

- `docs/TODO.md` defines `M6.5.3` with two artifact commands: `docker build -t portex:v1.0.0 .` and `cd web && npm run build`
- the repository currently has no root `Dockerfile`; only `container/agent-runner/Dockerfile` exists
- `scripts/build_docker.py` is still a placeholder and `Makefile` currently routes through it
- the local environment has no `docker`, `podman`, `nerdctl`, or `buildah` command, so container-image verification can only be static unless that changes
- `M6.5.2` intentionally left `v1.0.0` as a git tag while runtime/package strings remain `0.1.0`

## Options Considered

### Option A: Add a root backend runtime image and keep the frontend artifact separate

Pros:
- minimal change that matches the TODO commands directly
- avoids introducing a second process manager or static-file serving stack
- keeps frontend artifact production aligned with the existing `npm run build`
- preserves the existing runner image path without conflating it with the release image

Cons:
- final milestone evidence is split between a backend image artifact and a frontend `dist/` directory

### Option B: Build a single image that also serves the frontend

Pros:
- one image could represent more of the application surface

Cons:
- requires new static serving decisions not present in the current app
- would expand scope into process supervision, static hosting, or nginx-like wiring

### Option C: Only document the blocker and do no implementation

Pros:
- lowest risk

Cons:
- leaves the repository unable to satisfy the TODO command even in a Docker-enabled environment
- does not advance the artifact build path materially

## Recommended Design

Choose **Option A**.

## Proposed Changes

### Root release image

- add a root `Dockerfile` for the backend runtime image
- copy only the files needed for the FastAPI backend/runtime code path
- install Python dependencies from the root `pyproject.toml`
- run as a non-root `portex` user
- default entrypoint should start `uvicorn app.main:app`

### Build wrapper

- implement `scripts/build_docker.py` as a thin wrapper around `docker build`
- default behavior should target the new root release image with tag `portex:v1.0.0`
- allow `--file` and `--context` overrides so `Makefile` can still support the runner image path

### Frontend artifact

- keep `web/package.json` build behavior unchanged
- treat `web/dist/` as the frontend artifact for this milestone

### Static verification

- add tests for `scripts/build_docker.py` command generation and subprocess wiring
- add file-content tests that assert the root `Dockerfile` and `.dockerignore` contain the required scaffold
- run the real frontend production build and confirm `web/dist/index.html` exists
- if Docker remains unavailable, record the root image build as an external blocker rather than a completed runtime-verified artifact

## Risks and Boundaries

- because the local environment lacks a container runtime, this phase may end with the release-image path implemented but not fully smoke-tested
- the root release image will cover backend runtime only; the frontend artifact remains separate by design in this milestone
- `container/agent-runner/Dockerfile` remains valid for runner-specific work and should not be overwritten by the new root release image

## Expected Deliverables

- `Dockerfile`
- `.dockerignore`
- implemented `scripts/build_docker.py`
- updated `Makefile`
- tests covering the build wrapper and static Docker artifact scaffold
- updated release/deployment/handoff docs describing the new artifact boundary and any remaining Docker-runtime blocker
