# Portex 优先补齐路线图

最后更新：2026-03-08（Asia/Shanghai）

## 1. 文档目的

这份文档是在 `docs/portex-vs-happyclaw-gap.md` 的基础上，进一步回答一个更实际的问题：

> 如果目标是让 `Portex` 更快逼近 `happyclaw` 的产品能力，接下来最值得优先补齐哪些模块？

因此，这不是完整规格书，而是一份 **面向后续 Codex 直接执行的优先级路线图**。

---

## 2. 当前起点

截至当前状态：

- `M0` ~ `M3` 已完成
- `M4.1.1` ~ `M4.1.3` 已完成
- 当前起点：`M4.2.1`

已经具备的基础：

- 消息运行主链路
- WebSocket / 运行 / 取消流
- Docker / host mode 执行底座
- 挂载安全与生命周期管理
- 基础用户模型
- 管理员用户管理 API
- 最小邀请码系统

当前关键现实约束：

- Docker daemon 当前环境不可用，真实容器烟测仍未完成
- 用户和邀请码当前仍主要由 in-memory `AuthService` 承担运行态
- 邀请码当前是“可选消费”，尚未实现注册模式开关

---

## 3. 优先级判断原则

后续优先级按这三个标准排序：

### A. 是否会成为后续模块的前置依赖

例如 RBAC 如果不先做，后面的群组成员、管理权限、注册设置都会反复返工。

### B. 是否能把“已有骨架”变成“真正可用能力”

例如现在已有 `role`、admin 用户 API、邀请码 API，但还缺真正的权限语义与边界。

### C. 是否最接近 happyclaw 的产品短板

当前 Portex 与 happyclaw 的最大差距，不在执行底座，而在：

- RBAC
- 任务系统
- 记忆系统
- 注册/管理/配置闭环

---

## 4. P0：必须先补齐

## P0.1 `M4.2` RBAC 权限系统

### 对应 TODO

- `M4.2.1` 定义权限模板
- `M4.2.2` 实现权限检查装饰器
- `M4.2.3` 实现群组成员管理

### 为什么是第一优先级

这是当前最关键的“承上启下”模块。

原因：

- `M4.1` 刚完成用户、admin 管理、邀请码
- 这些能力现在本质上还是“字段和接口”
- 只有把角色真正映射为权限，后面的群组共享、任务边界、管理端能力才不会失控

### 预期产出

- `domain/permissions.py`
- `require_permission(resource, action)` 依赖
- 群组成员模型 `group_members`
- 基础权限检查逻辑
- 用户 / 邀请码 / 群组角色命名统一

### 实施建议

建议顺序：

1. 先完成权限模板常量
2. 再补 `require_permission`
3. 再落 `group_members`
4. 最后把现有 admin-only 路由逐步迁移到更细粒度权限

### 风险点

- 当前用户运行态仍在 in-memory `AuthService`
- 如果权限设计过早耦合 DB 实现，会把 `M4.2` 无谓扩大

建议做法：

- 先定义“权限契约”
- 暂时让权限判断兼容当前 in-memory 用户/邀请码体系
- 不在 `M4.2` 里顺手启动完整 DB 用户迁移

---

## 5. P1：紧随其后，直接提升产品能力

## P1.1 `M4.3` 定时任务系统

### 对应 TODO

- `M4.3.1` 实现任务调度器
- `M4.3.2` 实现任务 CRUD API
- `M4.3.3` 实现任务执行日志

### 为什么优先级高

如果 Portex 想从“聊天式远程 Agent”更接近 happyclaw 的“可调度工作系统”，任务系统是最直接的升级。

### 预期产出

- Scheduler 主循环
- `tasks` API
- `task_run_logs`
- cron / interval / once 的最小闭环

### 与前置模块的关系

- 需要依赖 `M4.2` 提供更合理的权限边界
- 但不要求先做完整配置系统

### 风险点

- 调度器与现有运行链路如何衔接
- 任务创建者、任务执行权限、跨组执行边界如何约束

建议：

- 先只支持最小任务闭环
- 权限先依赖 `M4.2` 的基础能力
- 暂不引入过重的分布式/复杂重试策略

---

## P1.2 `M4.4` 记忆系统

### 对应 TODO

- `M4.4.1` `CLAUDE.md` 管理
- `M4.4.2` 日期记忆
- `M4.4.3` 记忆搜索
- `M4.4.4` MCP 工具包装

### 为什么优先级高

happyclaw 的体验优势之一，不只是“能跑 Agent”，而是“能长期协作”。

记忆系统正是把 Portex 从“单次执行”推向“持续协作体验”的关键模块。

### 预期产出

- 用户级全局记忆
- 群组/日期记忆
- 基础搜索能力
- agent-runner 可调用的 memory 工具

### 风险点

- 文件目录约定需要与现有 `data/` 布局保持一致
- 后续还要与权限/群组成员共享模型衔接

建议：

- 先做简单且稳定的文件型记忆
- 搜索先做全文扫描即可
- 不要一开始就引入复杂索引系统

---

## 6. P2：补齐管理与产品闭环

## P2.1 注册控制与邀请码增强

### 当前缺口

虽然 `M4.1.3` 已完成最小邀请码系统，但离 happyclaw 还差：

- 开放注册 / 必须邀请码 / 关闭注册
- invite 删除
- 更强的邀请码策略
- 与权限模板更强绑定

### 建议位置

不建议把这些全部塞回 `M4.1.3` 补丁式扩展。

更合理的做法是：

- 在 `M4.2` 之后，
- 结合权限模板与管理端能力，
- 再补 registration settings / invite policy。

---

## P2.2 审计日志与管理端增强

### 当前缺口

Portex 还没有 happyclaw 那套更完整的管理平面：

- 审计日志
- 用户删除/恢复
- 注册设置
- 更完整的 admin API

### 建议时机

建议在 `M4.2`、`M4.3`、`M4.4` 之后补。

原因：

- 审计什么，取决于权限和任务/记忆这些核心业务先稳定
- 否则审计模型会不断返工

---

## P2.3 DB-backed 用户体系迁移

### 当前缺口

现在的用户与邀请码运行态仍依赖 in-memory `AuthService`。

这对当前阶段是合理的，因为它让 `M4.1` 能以最小代价落地；但长期来看，它会成为以下能力的限制：

- 登录会话持久化
- 用户禁用即时生效
- 权限持久化
- 审计日志关联
- 注册设置与邀请码策略

### 建议策略

不要现在立刻迁移。

建议等：

- `M4.2` 权限契约稳定
- `M4.3` / `M4.4` 基础闭环完成

再评估一次把用户、邀请码、权限状态迁移到 DB-backed service。

---

## 7. 当前推荐执行顺序

如果目标是“最快逼近 happyclaw 的关键产品能力”，推荐顺序如下：

### 第一阶段：先把权限地基补稳

1. `M4.2.1` 权限模板
2. `M4.2.2` 权限检查依赖
3. `M4.2.3` 群组成员模型

### 第二阶段：把系统从聊天式 Agent 变成工作系统

4. `M4.3.1` 调度器
5. `M4.3.2` 任务 API
6. `M4.3.3` 任务日志

### 第三阶段：补长期协作体验

7. `M4.4.1` 用户记忆
8. `M4.4.2` 日期记忆
9. `M4.4.3` 搜索
10. `M4.4.4` MCP memory 工具

### 第四阶段：补产品闭环和运营能力

11. 注册控制 / 邀请码增强
12. 审计日志
13. 更完整 admin 能力
14. DB-backed 用户体系迁移

---

## 8. 适合下一个 Codex 直接执行的版本

如果只保留最短行动建议，可以直接按下面执行：

### 当前最重要

- 从 `M4.2.1` 开始做 RBAC

### 当前不要顺手扩大的部分

- 不要在 `M4.2` 里顺手做完整 DB 用户迁移
- 不要在 `M4.2` 里顺手做注册设置全家桶
- 不要在 Docker daemon 不可用的情况下误报真实容器能力已烟测

### 当前最该保留的风险备注

- Docker 真实烟测仍未完成
- 用户/邀请码运行态仍主要由 in-memory `AuthService` 承担
- 邀请码目前只是“可选消费”的最小实现

---

## 9. 最短结论

如果后续开发只看一句话：

> Portex 当前最该优先补齐的是 `M4.2` RBAC，因为它决定了后面的任务系统、记忆系统、群组成员共享和管理端能力会不会反复返工；在此之后，再依次补 `M4.3` 任务系统和 `M4.4` 记忆系统，收益最高。
